\section{From an Agent Pipeline to a Multi-Agent System}

The previous section presented an agent-based pipeline in which a single LangChain agent
orchestrates two tools, \texttt{context\_tool} and \texttt{gap\_filler\_tool}, to solve the
gap-filling task. That design established the value of tool-mediated decomposition, but it
remains a \textit{single-agent} architecture: one planner, one language model and one
process hold every responsibility in the workflow.

In introducing that pipeline we noted that multi-agent systems extend the agent paradigm by
allowing several specialized agents to collaborate, exchange information and distribute
subtasks such as context retrieval, sequence generation and validation among cooperating
peers \cite{li2024survey}. This section realizes that extension. We describe a genuine
multi-agent system in which three specialized agents, each deployed on a separate compute
node of the ARES cluster and each owning the specific models its role requires, cooperate
to fill the same gaps. Although three agents constitute a minimal configuration, it is the
smallest one that exercises every mechanism a larger distributed deployment would require,
and Section~\ref{subsec:mas-scaling} examines what generalizes from it.

The motivation is not distribution for its own sake. Evaluating the single-agent pipeline
revealed a class of defect that the pipeline is structurally incapable of detecting:
because one process holds every responsibility, constraints that relate two of those
responsibilities are never expressed anywhere, and therefore never validated. The
multi-agent design forces those constraints across an interface, where they become
measurable. As shown in Section~\ref{subsec:mas-improvements}, the quantity that determined
whether retrieval augmentation functioned at all was never computed in the single-agent
pipeline, and becomes a measured, transmitted and verified value in the multi-agent one.

\subsection{Motivation: Limitations of the Single-Agent Pipeline}
\label{subsec:mas-motivation}

Five limitations of the agent-based pipeline motivated the redesign. Each is addressed by a
specific architectural decision described later in this section.

\begin{itemize}
    \item \textbf{Tool ordering was requested, not enforced}: the system prompt instructed
    the agent to call \texttt{context\_tool} before \texttt{gap\_filler\_tool}, but
    \texttt{AgentExecutor} imposes no ordering, sets no iteration limit and provides no
    failure handling. Nothing in the code verified that the requested sequence was
    followed.

    \item \textbf{The genomic payload passed through the language model}: the nucleotide
    string was interpolated into the prompt and the model was expected to reproduce it
    verbatim as an argument to the second tool. No checksum or length assertion protected
    it in transit.

    \item \textbf{Retrieval returned no matches}: \texttt{retrieve\_context()} performs a
    substring search rather than a similarity search, using Python's \texttt{in} operator.
    Measured over the full corpus of 37{,}645 records with the 50~bp flanks used by the
    test harness, this returns \textbf{zero} exact matches and zero partial matches. The
    retrieval-augmented condition was therefore indistinguishable from the condition
    without retrieval.

    \item \textbf{Retrieved context was discarded before inference}: the masked input was
    assembled as \texttt{\{left\} [MASKS] \{right\}\textbackslash n\textbackslash n\# Context:
    \{retrieved\}} and then tokenized with \texttt{truncation=True, max\_length=4096}.
    Because truncation removes tokens from the end, the retrieved context was the first
    content to be deleted. No error was raised, the execution completed, and the result was
    recorded as RAG-enabled.

    \item \textbf{The test harness selected non-adjacent contigs}: \texttt{test.py} used
    \texttt{contigs[0]} and \texttt{contigs[1]}. As the FASTA file is sorted by descending
    length, these are \texttt{contig31} (190{,}651~bp, genomic position 1{,}298{,}041 to
    1{,}488{,}692) and \texttt{contig22} (167{,}069~bp, position 898{,}138 to
    1{,}065{,}207), two contigs that are not adjacent and between which no gap exists.
\end{itemize}

The fourth limitation is the one that dictates the architecture that follows. The component
that knew the token budget of the masked language model and the component that selected the
reference sequences were the same function. Consequently, the constraint relating them was
never expressed: the number of retrieved records was the constant \texttt{k=2}, chosen
without reference to the available context window. A value that never crosses a component
boundary is never validated, never logged and never reported.

\subsection{Overview and Architecture}
\label{subsec:mas-architecture}

The multi-agent system distributes the workflow across three agents, each responsible for
one phase of the task and each hosting the specific models that phase requires. Agents
communicate using the Agent2Agent (A2A) protocol over HTTP, and every capability an agent
exposes is declared as a Model Context Protocol (MCP) tool.

The three agents are the following:

\begin{itemize}
    \item \textbf{Coordinator Agent}: executes policy rather than science. It loads no
    scientific models, constructs the retrieval query from the flanking contigs, verifies
    that its peers are operational and reading the same reference corpus, delegates the
    task, and applies an acceptance gate to the result.

    \item \textbf{Retrieval Agent}: owns the DNABERT-S embedder and the FAISS index over
    43{,}575 coding sequences. It answers requests for candidates with corpus row
    identifiers and cosine similarity scores, never with nucleotide sequences.

    \item \textbf{Reconstruction Agent}: owns the GENA-LM masked language model. Because it
    owns the tokenizer, it is the only component able to measure the available context
    budget, and it therefore drives the negotiation and performs the final prediction.
\end{itemize}

\subsection{Agent Communication: the A2A Protocol}

The A2A protocol defines how one agent requests work from another over standard HTTP with
JSON payloads, which removes the need for a message broker or a central coordinating
process. Three of its mechanisms are used here.

\begin{itemize}
    \item \textbf{Agent Card}: each agent publishes a discovery document at
    \texttt{/.well-known/agent-card.json} declaring its identity, its skills and the
    optional protocol features it supports. Our agents additionally publish a fingerprint
    of the reference corpus they have loaded, under the metadata key
    \texttt{x-corpus-fingerprint}.

    \item \textbf{Tasks}: a unit of work is a task with a unique identifier and a lifecycle.
    The specification defines nine states; our agents traverse \texttt{submitted},
    \texttt{working} and then \texttt{completed} or \texttt{failed}. A task in a terminal
    state cannot be restarted, which makes each execution auditable after the fact.

    \item \textbf{Messages and Artifacts}: requests carry typed parts. We use
    \texttt{DataPart} for structured JSON and \texttt{TextPart} for prose, and results are
    returned as artifacts containing both. All information the system depends upon travels
    in the \texttt{DataPart}; the prose is advisory and is consumed by nothing.
\end{itemize}

An abbreviated request from the coordinator to the reconstruction agent is shown below. The
contigs travel as structured data and are never rendered into a prompt, in contrast to the
single-agent pipeline, where the sequence was interpolated into the prompt text.

\begin{verbatim}
{"jsonrpc": "2.0", "id": "req-4f1c", "method": "message/send",
 "params": {"message": {
     "role": "user",
     "messageId": "msg-9a2e",
     "contextId": "ctx-1b7d",
     "parts": [{"kind": "data", "data": {
         "op": "reconstruct",
         "gap_id": "AP012051.1_gap1",
         "gap_length": 870,
         "left":  "TATTATCTTTCCGTTTGGCACAATT...",
         "right": "ATTGGCATTAAACCAGACATTGAAG...",
         "organism": ""}}]}}}
\end{verbatim}

The HTTP layer is implemented on the Python standard library
(\texttt{http.server.ThreadingHTTPServer}) rather than on a web framework, which keeps the
protocol modules importable without the agent SDK and therefore independently testable.

\subsection{Agent Capabilities: MCP Tools}

Every action an agent can take is declared as an MCP tool consisting of a name, a
description written for the language model, a parameter schema and a handler function. The
model reads the descriptions and decides which tool to invoke and when. Where the
single-agent pipeline exposed two tools to one planner, the multi-agent system distributes
thirteen tools across three agents, each seeing only its own.

A representative tool definition is shown below. The description is the only documentation
the language model receives, so it is written as an instruction rather than as a comment.

\begin{lstlisting}[language=Python]
@tool(
    "measure_budget",
    "Tokenize the model input with the context slot empty and report how many "
    "of the 4096 token positions are free for retrieved context. Must be called "
    "before requesting or admitting any candidates.",
    {"task_id": str},
)
@guarded("measure_budget", requires=None)
async def measure_budget(args: dict, state: ReconTask) -> dict:
    base = mlm.build_model_input("", state.model_left, state.model_right)
    base_tokens = await run_blocking(mlm.count_tokens, tokenizer, base)
    free = config.MAX_LENGTH - base_tokens - seed - config.SAFETY_TOKENS
    state.free_tokens_remaining = max(0, free)
    state.advance(Phase.MEASURED)
    return errors.tool_ok({"base_tokens": base_tokens, "free_tokens": free})
\end{lstlisting}

\subsection{Specialized Agents and Their Surrogate Models}

A defining property of the multi-agent design, and the principal difference from the
single-agent pipeline, is that each agent hosts the specific models its role requires and no
others. These are \textit{surrogate models}: trained networks that stand in for computations
that are exact in principle but prohibitively expensive to perform directly. The language
model inside each agent performs none of this scientific computation; it decides when the
surrogates are invoked and with which parameters.

\subsubsection{Retrieval Agent: \texttt{agents/retrieval.py}}

This agent hosts one surrogate models.

\begin{itemize}
    \item \textbf{DNABERT-S, a surrogate for sequence alignment}: determining whether two
    DNA sequences are related is solved exactly by pairwise alignment, which for a
    1{,}800~bp query against 43{,}575 references requires tens of millions of character
    comparisons. DNABERT-S instead maps any sequence to a fixed vector of 768 real values,
    reducing the comparison to a dot product. The model was trained contrastively, so that
    sequences from the same organism are drawn together in the embedding space and sequences
    from different organisms are separated, which is precisely the property a similarity
    search requires.

\end{itemize}

The correctness of the retrieval surrogate was verified by querying the index with reference
sequences it already contains and confirming that each is returned as its own nearest
neighbour.

\begin{table}[H]
\centering
\begin{tabular}{lll}

\midrule

The agent exposes \texttt{retrieve\_context()}, which embeds the query once and ranks the
corpus, and \texttt{extend\_context()}, which serves subsequent batches from the same ranking
without repeating the embedding step. Both return only row identifiers and scores. Resolving
an identifier to a nucleotide sequence is the responsibility of the consumer, which prevents
corpus DNA from crossing an agent boundary as an opaque block. This is a direct contrast with
the single-agent design, where \texttt{retrieve\_context()} returned concatenated sequences
that the caller could only accept or lose in their entirety.

\subsubsection{Reconstruction Agent: \texttt{agents/reconstruction.py}}

This agent hosts the third surrogate, GENA-LM BigBird, the same masked language model used in
the single-agent pipeline. It stands in for the true sequence of the gap, which could
otherwise be obtained only by resequencing the organism, by producing the nucleotides that
are most plausible given the surrounding context.

Because this agent owns the tokenizer, it is the only component that can determine how much
context fits, and it therefore implements the following operations:

\begin{itemize}
    \item \texttt{measure\_budget()}: tokenizes the input with the context slot empty and
    subtracts from the 4{,}096 token limit.
    \item \texttt{request\_candidates()} and \texttt{extend\_candidates()}: issue A2A requests
    to the retrieval agent, sized according to the measured budget.
    \item \texttt{admit\_candidates()}: resolves the returned identifiers against its own copy
    of the corpus, tokenizes each candidate and admits those that fit.
    \item \texttt{generate()}: performs the masked prediction over the admitted context.
\end{itemize}

of the system.

\subsection{Enforcing Correctness: \texttt{runtime/state.py}}

Placing a language model in control of the workflow reintroduces the first limitation
identified in Section~\ref{subsec:mas-motivation}. Three rules prevent this, none of which is
expressed as a written instruction.

\begin{itemize}
    \item \textbf{Results are read from state, not from generated text}: each tool writes into
    a per-task record, and the A2A response is serialized from that record by ordinary code.
    The prose produced by the model is attached to the artifact and consumed by nothing. This
    proved necessary in practice: during development one retrieval invocation terminated with
    an error message instead of a summary \textit{after} its tool had already executed, and the
    task nevertheless completed correctly with the expected record identifiers.

    \item \textbf{Ordering is a data dependency}: every tool begins with a precondition check
    and performs no work if the prerequisites are absent. The refusal is a structured value
    naming the tool that must be called instead.

    \item \textbf{Sequences are never tool arguments}: every tool is keyed by a task
    identifier, and the contigs, the query and the retrieved sequences reside in agent state.
    The model determines \textit{when} a search occurs, not \textit{what} is searched for.
\end{itemize}

A representative refusal is shown below.

\begin{verbatim}
{"error": "PRECONDITION_FAILED",
 "code": "BUDGET_NOT_MEASURED",
 "phase": "CREATED",
 "required_phase": "MEASURED",
 "remedy": "Call mcp__reconstruction_agent__measure_budget with this
            task_id first; it reports how many tokens are free for
            retrieved context."}
\end{verbatim}

The most significant of these checks concerns the budget. To admit candidates, the model must
supply the number of free tokens, and any value other than the one the agent currently holds
is rejected. Since that value can be obtained only by calling \texttt{measure\_budget()}, the
dependency cannot be circumvented. A second check rejects any gap length other than the one
with which the task was created, which is the precise defect present in
\texttt{planner\_tools.py}, where an adjusted length silently replaced the requested one.

\subsection{The Negotiation Loop}
\label{subsec:mas-negotiation}

The interaction between the reconstruction and retrieval agents is the defining feature of
the multi-agent design and has no counterpart in the single-agent pipeline. Neither agent can
determine alone how many reference sequences to use: the retrieval agent knows the ranking but
not the tokenizer state, and the reconstruction agent knows the budget but has no access to
the corpus.

\begin{enumerate}
    \item The reconstruction agent tokenizes the input with the context slot empty and
    determines that \textbf{3{,}236 of 4{,}096 token positions are free}.
    \item It requests candidates from the retrieval agent with a batch size appropriate to
    that budget. The retrieval agent embeds the query once, ranks the corpus and returns the
    first ten row identifiers with their similarity scores.
    \item The reconstruction agent resolves those identifiers locally, tokenizes each
    candidate, admits those that fit and reports the remaining capacity.
    \item Capacity remains, so it requests a further batch. The retrieval agent serves the next
    segment of the same ranking without repeating the embedding step.
    \item The loop terminates when the context window is full or the ranking is exhausted, and
    the prediction is performed.
\end{enumerate}

The following trace was recorded during a three-node execution. The batch sizes decrease as
the remaining budget decreases; no instruction specified these values, and the model derived
them from the preceding response.

\begin{verbatim}
 1. measure_budget       ok  phase=MEASURED    +7.9s   3236 tokens free
 2. request_candidates   ok  phase=MEASURED   +24.6s   served 10 of a 40 row pool
 3. admit_candidates     ok  phase=ADMITTING  +31.3s
 4. extend_candidates    ok  phase=ADMITTING  +47.6s   served  5  (total 15)
 5. admit_candidates     ok  phase=ADMITTING  +51.2s
 6. extend_candidates    ok  phase=ADMITTING  +66.0s   served  2  (total 17)
 7. admit_candidates     ok  phase=ADMITTING  +70.0s
 8. generate             ok  phase=GENERATED +184.7s   872 nucleotides produced
\end{verbatim}

The outcome is that \textbf{2{,}942 of the 3{,}236 available token positions were occupied by
retrieved context}, corresponding to 91\% of the budget. Under the fixed \texttt{k=2} of the
single-agent pipeline, approximately 350 tokens would have been used, or 11\%, and no
measurement of either figure would have been produced.

\subsubsection{Prompt Assembly: \texttt{tools/mlm.py}}

Two modifications ensure that the admitted context survives tokenization. First, the context
is placed at the beginning of the input rather than appended, so that truncation, which
removes from the end, cannot reach it.

\begin{lstlisting}[language=Python]
def build_model_input(context: str, left: str, right: str) -> str:
    """Context first, then the flanks surrounding the mask slot."""
    head = f"{context.strip()} " if context.strip() else ""
    return f"{head}{left} [MASKS] {right}"
\end{lstlisting}

Second, the flanking contigs are truncated to 2{,}000~bp on each side before assembly. The
effect on the available budget for gap~1 of AP012051.1 is shown below.

\subsection{Acceptance Gate: \texttt{gate.py}}

The single-agent pipeline applied no acceptance criterion; whatever the model produced was
returned. The coordinator now evaluates three conditions before releasing a result.

\begin{lstlisting}[language=Python]
def evaluate(produced: str, gap_length: int, context_tokens_admitted: int,
             tolerance: float = 0.05) -> tuple[bool, list[str]]:
    reasons = []
    if not produced:
        reasons.append("EMPTY")
    else:
        if abs(len(produced) - gap_length) > tolerance_bases(gap_length, tolerance):
            reasons.append("LENGTH")
        if not set(produced) <= {"A", "C", "G", "T", "N"}:
            reasons.append("ALPHABET")
    if context_tokens_admitted <= 0:
        reasons.append("NO_CONTEXT")
    return (not reasons), reasons
\end{lstlisting}

The third condition, that the number of admitted context tokens must be greater than zero, did
not exist previously and is the principal contribution of the redesign. It converts the claim
that an execution used retrieval from a label into a verified precondition. The resulting
verdicts are deliberately distinguishable: \texttt{REJECTED:NO\_CONTEXT} indicates a defect in
the orchestration, whereas \texttt{REJECTED:LENGTH} indicates that the surrogate generator
produced an implausible output.

\subsection{Deployment on ARES: \texttt{deploy.sh}}

The three agents are deployed one per compute node. Node allocation is handled by SLURM, and
the shared filesystem makes the code, the reference corpus and the credentials visible from
every node without staging.

\begin{verbatim}
# 1. reserve three compute nodes
salloc -N 3 -p compute -t 02:00:00 --no-shell -J genomio-mas
#    -> Granted job allocation 22917, nodes ares-comp-[10-12]

# 2. preflight each node, launch one agent per node, wait for readiness
./multiagent_system/deploy.sh 22917

# 3. execute the test
multiagent_system/.venv/bin/python3 multiagent_system/test.py --mode slurm

# 4. release the allocation
scancel 22917
\end{verbatim}

The deployment script never hard-codes node names; it queries the allocation, assigns one role
per node, computes each agent's endpoint and records them for the test to read. Before any
agent is started it verifies on every node that the Python environment imports correctly, that
the credentials are present and that the reference index is accessible, aborting the launch if
any check fails.

[deploy] placement: one-per-node

\subsection{Pipeline Execution Flow}

Once a gap specification is submitted to the coordinator, the following steps occur.

\begin{enumerate}
    \item The coordinator constructs the retrieval query from 900~bp on each side of the gap,
    confirms that both peers are operational and compares the corpus fingerprints they publish.
    \item It delegates the task to the reconstruction agent over A2A, transmitting the contigs
    and the gap length as structured data.
    \item The reconstruction agent measures the available token budget.
    \item It negotiates candidate batches with the retrieval agent, admitting those that fit,
    until the window is full or the ranking is exhausted.
    \item It performs the masked prediction and returns the sequence together with the counters
    describing how it was produced.
    \item The coordinator applies the acceptance gate and emits the execution record.
\end{enumerate}

\subsection{Improvements over the Single-Agent Pipeline}
\label{subsec:mas-improvements}

The improvements derive from two independent properties of the multi-agent design: that there
are specialized agents, and that each agent owns the specific models its role requires.

\subsubsection{Improvements arising from specialized agents}

\begin{itemize}
    \item \textbf{A previously non-existent quantity is now measured}: because the component
    holding the tokenizer and the component ranking the references are separate processes, the
    token budget must be transmitted between them, and consequently it is computed, sent and
    recorded. The multi-agent structure did not improve this calculation; it caused the
    calculation to exist.

    \item \textbf{Fixed constants are replaced by negotiation}: candidates are served
    incrementally in response to the measured budget rather than as a fixed \texttt{k=2},
    raising context window utilization from approximately 11\% to 91\%.

    \item \textbf{Rules are enforced at an interface}: preconditions apply to a remote peer
    exactly as to a local caller. An out-of-order request is refused before any search is
    performed, and in one recorded instance the refusal occurred before the peer was contacted
    at all. Within a single process, an ordering rule is a convention that subsequent
    modification may silently violate; across an interface it forms part of the contract.

    \item \textbf{Failures remain localized}: an error in one agent's language model does not
    terminate the execution, as the remaining agents are separate processes with independent
    state. In the single-agent pipeline, a failure in the one language model driving all steps
    ends the run.

    \item \textbf{Inconsistencies between components become detectable}: because the two peers
    load the reference corpus independently, they could hold different versions of it, in which
    case a row identifier would denote a different gene to each. Each agent therefore publishes
    a corpus fingerprint and the coordinator compares them before delegating. This verification
    is meaningless within a single process, where only one copy exists. Separation created the
    risk and simultaneously made it checkable.

    \item \textbf{Executions are auditable across machines}: every task carries a shared context
    identifier, so records produced on three different nodes join on a single key. The
    negotiation trace in Section~\ref{subsec:mas-negotiation} was reconstructed from these
    records rather than from console output.

    \item \textbf{Components are independently testable}: the system includes 154 unit and
    contract tests that execute in approximately three seconds without loading any scientific
    model or invoking any language model, because each tool can be called directly and each
    precondition verified in isolation.
\end{itemize}

\subsubsection{Improvements arising from agent-specific models}

\begin{itemize}
    \item \textbf{Surrogate models remain resident}: loading occurs once per agent rather than
    once per request, yielding similarity searches 83 times faster than those requiring a cold
    model load.

    \item \textbf{Each model is co-located with the data it requires}: the embedder resides with
    the index constructed from it, so their correspondence is an internal invariant rather than
    a runtime contract; the generator resides with the tokenizer that measures its budget, which
    is what renders that budget measurable at all.

    \item \textbf{Resources are allocated according to demand}: three components with footprints
    of 0.12, 1.0 and 1.2~GB and startup costs of 2, 33 and 3~seconds each receive a dedicated
    40-core node rather than competing for one.

    \item \textbf{Startup is amortized}: the fleet becomes ready in 51~seconds and remains
    available, so subsequent executions against the same deployment report readiness
    immediately.

    \item \textbf{Components are independently replaceable}: because each agent is reached only
    through a documented protocol endpoint and advertises its capabilities through an agent
    card, it can be restarted, relocated or reimplemented without modifying its peers.
\end{itemize}

\subsection{Towards a Larger Distributed Multi-Agent System}
\label{subsec:mas-scaling}

The three-node deployment described here is deliberately minimal, but it is not a special
case. It is the smallest configuration that exercises every mechanism a larger distributed
multi-agent system would require, and it therefore constitutes an initial approach to
systems in which many agents, each with its own models and its own hardware requirements,
are distributed across a much larger set of machines.

Several properties of the implementation are independent of the number of agents.

\begin{itemize}
    \item \textbf{No component knows how many agents exist}: agents address one another by
    endpoint, and each publishes an agent card describing its identity and skills. Nothing
    in the agent code refers to a fixed topology, and adding a fourth role would consist of
    writing its tools and registering its endpoint.

    \item \textbf{Placement is derived, not declared}: the deployment script queries the
    SLURM allocation, assigns one role per node and computes each endpoint. Node names are
    never hard-coded, so the same script operates over any allocation the scheduler
    provides.

    \item \textbf{The transport imposes no shared infrastructure}: communication is HTTP
    with JSON payloads. There is no message broker, no shared memory segment and no central
    coordinating process. Two agents require only mutual network reachability, which means
    they need not reside on the same cluster.

    \item \textbf{The protocol is an open standard}: because agents interoperate through
    A2A and declare their capabilities through MCP, an agent may be replaced by an
    implementation written in a different language or built on a different framework
    without modifying its peers. This is the property that makes heterogeneous, multi-team
    deployments feasible.

    \item \textbf{Divergence between distributed copies is already anticipated}: the corpus
    fingerprint exchanged before delegation exists precisely because two agents hold
    independent copies of the reference data. That check becomes more valuable, not less,
    as the number of machines increases.
\end{itemize}

The deployment also demonstrates heterogeneous resource allocation, which is the principal
motivation for distributing a scientific multi-agent system in the first place. The three
agents differ by an order of magnitude in memory footprint and by more than a factor of ten
in startup cost, and each receives hardware appropriate to its role. This generalizes
directly: a larger system could place a generation agent on a GPU node, several retrieval
agents on memory-rich CPU nodes, and lightweight policy agents on whatever capacity remains,
with each agent loading only the models its role demands.

Two extensions follow naturally from the present design. The retrieval agent could be
replicated, since its ranked pools are held per request and independent of one another, with
requests distributed across replicas. Independently, multiple gaps could be processed
concurrently, as retrieval can serve one request while reconstruction generates for another;
the negotiation loop already tolerates this, although it was not evaluated here.

Three limitations would need to be addressed before the system could be described as
scaling to a large number of agents.

\begin{itemize}
    \item \textbf{Discovery is static}: endpoints are computed by the deployment script and
    supplied at startup. A2A defines the agent card but not a registry, so a larger
    deployment would require a discovery service through which agents announce themselves
    and are located dynamically.

    \item \textbf{Communication is point-to-point}: with $N$ agents the number of potential
    direct connections grows quadratically. Beyond a modest number of agents this motivates
    an intermediary such as an agent gateway, which would also provide a natural place for
    authentication and routing policy.

    \item \textbf{There is no authentication}: the current deployment relies on the ARES
    compute nodes being unreachable from outside the allocation. Any deployment spanning
    administrative domains would require the security schemes that A2A defines and that this
    implementation declares as empty.
\end{itemize}

None of these limitations affects the results reported above, since all three agents operate
within a single trusted allocation. They delimit the path from the present three-node
configuration to a genuinely large distributed system rather than qualifying what has been
demonstrated.

\subsection{Outcome and Limitations}

The multi-agent redesign achieved its objective. The quantity of retrieved evidence delivered
to the masked language model, which was neither computed nor reported in the single-agent
pipeline and which the truncation defect reduced to zero on any sufficiently long contig pair,
is now measured on every execution, transmitted between agents, verified by an acceptance gate
and recorded in the execution trace. Tool ordering is enforced by preconditions rather than
requested in a prompt, and no genomic sequence is handled by a language model at any point.

Several limitations remain and delimit the scope of these results.

\begin{itemize}
    \item \textbf{The acceptance gate verifies delivery, not biological correctness}: it
    confirms that retrieved evidence reached the model, that the produced length is plausible
    and that the output is a valid nucleotide string. It makes no assessment of whether the
    reconstruction is biologically accurate, and no such measurement is reported here, since
    the single-agent pipeline computed none for this test case and no baseline for comparison
    therefore exists.

    \item \textbf{The generator itself is unchanged}: the masked prediction procedure was
    retained deliberately, so that any change in behaviour is attributable to the four
    modifications made around it, namely the position of the context, the counters returned,
    the sampling threshold becoming a parameter, and the initial mask count being measured
    rather than assumed.

    \item \textbf{No throughput benefit for a single gap}: one gap requires approximately
    212~seconds, the majority of which is the prediction itself, which executes on a single node
    and cannot be subdivided. Concurrent processing of multiple gaps would pipeline naturally,
    as retrieval can serve one request while reconstruction processes another, but this was not
    evaluated.

    \item \textbf{Single task per agent}: a process-global model lock restricts each agent to
    one task at a time. Concurrent execution would require either per-task model instances or a
    request queue.
\end{itemize}

These limitations concern the surrogate models and the evaluation methodology rather than the
orchestration. The contribution of this section is infrastructural: moving from a single agent
holding every responsibility to specialized agents, each owning the specific models its role
demands, transforms quantities that were previously implicit into quantities that are measured,
transmitted and verified.
